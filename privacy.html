Privacy policy

Good Life OS is a single-user application. Its only user is the person who built and runs it, on their own computer. This policy describes what the application does with data — how it is collected, stored, used, disclosed, shared, retained and deleted.

Status at the date below: the Oura connection is enabled and in use, and Oura data has been synced to the operator's computer. The sections below describe how that data is handled, not how it would be.

Who operates it

Good Life OS is operated by Ashlandiam, acting as a private individual, for their own personal use. It is not a company or a commercial service. Questions can be sent to ashlandiam@gmail.com.

What data is involved

  • Information the operator types in: weigh-ins, daily check-ins (energy, mood, hunger and stress ratings, water, optional bloating and pain ratings, an optional note), and daily nutrition totals.
  • Oura data, once that connection is enabled and used: covering only the operator's own account. The permissions requested are listed below, together with the measurements they cover.

The application requests these five Oura permissions and no others: daily, heartrate, spo2, heart_health and stress. The request always names them explicitly. It is never left blank, because a blank request would ask Oura for every permission the account can grant, including personal details and email, which this application does not want and does not use.

Between them, those permissions cover:

  • Daily sleep, readiness and activity summaries — the sleep score, the readiness score, body-temperature deviation from the operator's own baseline and the longer-run temperature trend deviation, daily steps, active and total calories, and how the day divided into resting, sedentary and non-wear time.
  • Sleep-period detail, for each period separately — when it began and ended, time asleep and time in bed, time awake, how long was spent in deep, light and REM sleep, how long it took to fall asleep, a sleep efficiency figure, average and lowest heart rate, average heart-rate variability, average breathing rate, and a count of restless periods.
  • Heart rate measured across the day, not only during sleep.
  • Blood-oxygen average recorded during sleep, and the breathing disturbance index derived from it.
  • Cardiovascular measures — predicted vascular age, pulse wave velocity and VO2 max.
  • Daily stress and resilience summaries, including the sleep-recovery, daytime-recovery and stress figures behind the resilience level.

Which permission governs which measurement is not fully documented by Oura, and Oura's published API specification does not currently list a stress permission even though its developer portal offers one. The application therefore records what it was actually able to read, rather than assuming that a granted permission implies available data. Where a measurement cannot be read, it is shown as unavailable together with what was observed — a refusal or an empty result — and never as a zero.

No data about any other person is collected, at any point. The application has no other users, so it holds no other person's data.

How it is collected

Typed entries are collected as they are entered. Oura data is collected from Oura's API version 2, over an encrypted connection, and only after the operator has explicitly granted access through Oura's own authorisation screen. The application never sees or handles an Oura password.

Authorisation happens through Oura's standard OAuth flow. Before the browser is opened, the application shows the exact permissions it is about to request, so the request is visible rather than implied. Oura's authorisation screen then shows what is being granted, and access begins only if the operator approves it there.

What leaves the computer

Stating this precisely, because "nothing is transmitted" would be false.

The application runs a web server on the operator's own computer, bound to the loopback interface so that it is reachable only from that computer. During Oura authorisation it also runs a second, short-lived local listener to receive the authorisation response; that listener shuts down as soon as the exchange completes.

Outbound, the application contacts exactly one destination: Oura's API. Those requests carry the application's credentials, the authorisation code during sign-in, the access token on each data request, and the date ranges being requested. They are sent over an encrypted connection.

No other destination is contacted. There is no analytics, no telemetry, no crash reporting, no advertising or tracking component, and no third-party service of any kind.

Health records are never uploaded. There is no hosted dashboard, no account server and no remote copy of the database. The records are written to a file on the operator's computer and stay there.

How it is stored

In a SQLite database file in the operator's own user library folder, on the operator's computer, along with local backup snapshots of that file.

Each Oura record is also kept in the form Oura sent it, reduced to the fields listed above together with the record's own identifier and date. Fields the application does not use are discarded rather than stored — among them a minute-by-minute trace of movement and metabolic rate. Keeping the reduced record means the figures above can be rebuilt on the computer without asking Oura for them again.

That rebuilding is available only for records synced after this retention began. Older records remain available, but cannot be rebuilt from retained payloads unless fetched again.

Oura access credentials are stored in the macOS Keychain. They are never written to the database, never written to a backup, and never written to a log.

How it is used

Solely to display the operator's own information back to them — current figures, trends over time, and how complete each day's record is.

The data is never used to train, fine-tune, develop or evaluate any AI or machine-learning model. It is never combined with data about any other person. It is never used for advertising, marketing, profiling or research.

How it is disclosed and shared

It is not disclosed or shared with anyone. Nothing is sent to the developer, because the developer and the user are the same person and the records never leave their computer.

The operator can export their own records as CSV files. Those files are written to their own computer, and what happens to them afterwards is entirely the operator's choice.

How long it is retained

Information the operator types in is kept until the operator deletes it.

Synced Oura data is likewise kept on the operator's computer until the operator deletes it, so that long-run trends remain available. It is kept for no purpose other than showing the operator their own history.

How it is deleted

The application provides two separate actions, because they are different things and one should not silently perform the other:

  • Disconnect Oura. Stops all syncing and removes the stored Oura credentials from the Keychain. Existing synced Oura history remains in the local database, and the application says so plainly at the moment of disconnecting rather than leaving it to be assumed.
  • Delete Oura data. Removes every synced Oura record from the local database. This is offered on its own, and can be used whether or not the connection is still active.

Deletion is not complete until backups are cleared

This is stated directly rather than buried, because it is the part that is easy to get wrong.

The application keeps local backup snapshots of its database. A snapshot taken before a deletion still contains whatever was deleted afterwards. Removing records from the live database does not reach backwards into copies already written.

So deleting Oura data is treated as one operation covering both: the application removes the records from the live database and then clears them from every local backup snapshot that contains them, rewriting each snapshot without those records.

If any snapshot is not cleared — because the operator declines, or a snapshot cannot be rewritten — then the deletion is not complete, and the application does not describe it as though it were. It names each snapshot that still contains Oura data and continues to report that state until those snapshots are cleared or deleted. Backups are ordinary files and can also simply be deleted, which removes their contents entirely.

Withdrawing access

Access to Oura data can be withdrawn at any time, in either of two places, and neither depends on the other:

  • In Good Life OS, using Disconnect Oura, which stops syncing immediately and removes the stored credentials.
  • In the Oura account itself, by revoking the application's authorisation at cloud.ouraring.com. Revoking there takes effect immediately and prevents any further access, whatever the application does.

Withdrawing access carries no penalty and does not affect the operator's Oura account, ring or subscription in any way. Withdrawing access stops further collection; deleting data already collected is the separate action described above.
